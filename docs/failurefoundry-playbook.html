FAILUREFOUNDRY — INTERNAL BRIEFING TRACK: AI FOR FINANCE

The FailureFoundry Playbook

A working reference for the team: what's actually built, how to walk a judge through it, and the questions to have answers for before you're standing in front of one.

PRISM finds and explains the failure. FailureFoundry turns that diagnosis into an executable behavioral contract that prevents recurrence. — the one line every screen, PR, and demo beat has to earn

01

The pitch, in one breath

Every AI-reliability tool at this hackathon will show you a dashboard that says a model was unfair or unsafe. None of them will show you the model structurally unable to see the thing that made it unfair — and then prove, on the next run, that it still can't.

That's the gap FailureFoundry sits in. FairClaim (the insurance pipeline) is the demonstration environment, not the product. The product is the pipeline that runs underneath it: PRISM diagnoses a failure → FailureFoundry compiles that diagnosis into a versioned Behavior ABI → the ABI is enforced at runtime (proxy fields are actually stripped from the agent's context, not flagged after the fact) → the fix is hardened against harder variants → the original failure becomes a permanent regression test → a release gate blocks any future version that regresses.

The "crazy" part to lean on in the room: this isn't a claims app with a fairness checkbox. It's a compiler. The input is a diagnosed failure. The output is executable code that changes what an agent is structurally capable of doing.

02

The five-minute demo, beat by beat

This is the version to actually rehearse. It starts where a judge starts — the customer portal, not the engineering console — because "I filed a claim and the system checked itself" lands harder than opening on an admin dashboard.

0:00

File a real claim

Open /users. Don't reach for a sample claim — upload an actual photo, pick a peril and damage severity, hit submit. This is a real multipart upload creating a real Policy + Claim + Document row, not a canned response.

POST /api/demo/claims/custom
0:45

Watch the decision resolve

The result page reveals the causal chain (Intake → Adjudication → Explainability → Verification) as a timeline, then the decision and a plain-English "why" — no jargon, no internal IDs leaking into the copy.

1:30

Open the fairness certificate

Tap the trust badge. This re-runs the same claim with the claimant's name, city, and narrative style swapped — nothing else — and shows whether the decision or payout moved. This is the counterfactual test from CLAUDE.md §13, run live, on this exact claim, in front of them.

POST /api/demo/fairness-groups/{id}/check
2:15

Toggle protection off

Same claim, same facts, protection off. Payout diverges purely on the proxy variant. This is the "holy shit" moment — say the sentence from §30 out loud: not "the dashboard says ZIP affected the decision," but "ZIP is structurally unavailable to this agent once the ABI is enforced, and here it is available again with it off."

3:00

Jump to the engineering console

Click "Verify this trace in the engineering console" on the receipt. It deep-links straight into Agent Runs, pre-filtered to this claim_id — the exact run rows, not a re-staged version of them.

?view=runs&claim_id=...
3:45

Show the failure → ABI → regression chain

Failures page → the registered fairness failure → its Behavior ABI (prohibited: ZIP, name, narrative_style) → the regression test that now exists because of it, permanently, in the suite.

4:20

Land on the release gate

PASS or BLOCKED, with the actual violated clause and the PRISM evidence backing it — not a green checkmark asserted for effect.

4:50

Close on the one-liner

"PRISM found it. FailureFoundry made it impossible to happen the same way twice." Stop talking. Let the release gate screen sit there.

03

The moment that actually sells it

Judges have seen fairness dashboards. What they haven't seen as often is the same claim, same facts, two different runtime realities, side by side:

PROTECTION OFF — v1 CONTEXT

Adjudication's context object contains claimant_name, zip, narrative_style. Identical legitimate facts, payout diverges across the counterfactual pair.

PROTECTION ON — ABI ENFORCED

Those keys are absent from the context object entirely before the agent ever reasons — not filtered from the output, removed from the input. Payout is identical across all four variants.

If a judge asks "couldn't the model just learn to infer that from the writing style anyway" — that's a real, fair question. The honest answer: the ABI's invariant check doesn't just remove the field, it also asserts pairwise decision/payout consistency across the counterfactual group and fails the release gate on any disparity — so a model that re-derives the proxy some other way still gets caught downstream, at the regression stage, not just at the input-filtering stage.

04

What's actually built — the insurance system

Four agents, each with one job, none of them able to do another's job:

Intakeagents/intake.py
Turns messy input (form fields, an uploaded photo, a description) into a structured claim: damage part, severity, estimated cost, evidence completeness. Never decides anything. On a freshly-submitted portal claim with no dataset ground truth, a dedicated _run_intake_user_submitted path avoids the visual-abstention logic built for the historical dataset — no photo escalates for evidence, a photo with complete evidence structures the claim.
Adjudicationagents/adjudication.py
The one agent that decides. Runs the deterministic oracle first — policy inactive → DENY, peril excluded → DENY, evidence missing → ESCALATE, else payout = min(verified_damage − deductible, coverage_limit) — then reasons within whatever factors the ABI currently permits into its context.
Explainabilityagents/explainability.py
Writes the customer-facing "why," cites only evidence that exists on this claim, and is checked for unsupported claims before a customer ever sees it. Now also grounds against a real PRISM Knowledge Base (teammate's contribution) rather than free-associating.
Appealsagents/appeals.py
Cannot overturn a decision without material new evidence — an appeal that just re-argues the same facts gets routed to escalation, not a silent reversal.
05

What's actually built — FailureFoundry core

Scenario Engine
Generates the counterfactual fairness pairs and workflow-bypass scenarios that everything downstream measures against.
Failure Detection
Runs matched claims through both agent versions and flags a failure when identical legitimate facts produce different decisions, payouts, or explanations.
Behavior ABI Compiler
Turns a diagnosed failure into a versioned, typed contract — permitted factors, prohibited factors, invariants, release constraints — that is validated on compile, not hand-written prose.
Enforcement Layer
The part that makes the ABI real: proxy fields are stripped from Adjudication's context object before it ever reasons. Verifiable by inspecting the context dict before and after — the fairness certificate feature is this check, run live, per claim.
Hardening
The fairness ladder — ZIP alone, then + name, then + narrative style, then + incomplete evidence — proves the fix generalizes past the one example that triggered it.
Regression Engine
Every discovered failure is persisted permanently. A fairness check that finds a disparity in the portal doesn't just show a badge — it calls register_regression_test for real, so it's in the suite from that moment on.
Metrics Engine
Task correctness, pairwise consistency, decision/payout disparity, workflow compliance, evidence completeness — computed from actual run rows, never hard-coded.
Release Gate
PASS only if critical ABI violations = 0, regressions pass, hardened scenarios pass, and required PRISM evidence was actually fetched. Otherwise BLOCKED, with the specific clause and evidence named.
06

PRISM — what it does here, and what it doesn't

FailureFoundry never re-implements evaluation or scoring — that line is deliberate, and worth stating plainly if asked. PRISM observes, evaluates, and diagnoses; FailureFoundry compiles, enforces, hardens, and gates. Integration runs on the real installed SDK (prismtrace.PRISMtrace, package blockconvey-monitor) against a live account, not a stub.

What's real right now: trace submission per run (submit_to_prism, opt-in so bulk/regression jobs don't burn quota), a fairness-check flow that submits real traced Adjudication calls, and — from a teammate's latest commit — the Release Gate now consumes an actual PRISM verdict, a live re-evaluation endpoint, and Explainability grounds against a real PRISM Knowledge Base instead of an ungrounded prompt.

HONEST GAP — SAY THIS IF ASKED, DON'T HIDE IT

Some PRISM endpoints used here (like /api/trajectories listing) are empirically verified against the installed SDK rather than publicly documented. CLAUDE.md's own rule (§21/§31) is to build around what's verified and never fabricate what isn't — that's exactly what happened, and it's a better answer than pretending every corner of the integration is fully documented.

07

The customer portal — why it's not a toy form

The credibility risk with any demo portal is "is this hardcoded." Three specific choices close that gap, and are worth naming to a judge unprompted rather than waiting to be asked:

Real random sourcing

GET /api/demo/claims/random pulls from the full ~2,500-row dataset and reports the true total claim count, not the 8 curated samples shown by default — provably not a fixed demo set.

Real free-form intake

A judge can upload their own photo and fill in real vehicle/peril/damage details. POST /api/demo/claims/custom creates a genuine Policy + Claim + Document, and the oracle math runs on their numbers, not a lookup table.

Receipts that point at their own proof

Every result carries a receipt — run count, agent version, a PRISM-submitted checkmark when true — with a deep link straight into the engineering console's Agent Runs page, pre-filtered to that exact claim. The claim someone just made a decision on and the trace rows backing it are the same rows, one click apart.

The fairness certificate and "what would change this"

Added this session, deliberately scoped to two things and nothing from the larger draft proposal (no Google auth, no email, no second admin surface — evaluated and cut as scope that doesn't earn its complexity for a hackathon judge): a per-claim counterfactual re-run against real proxy variants, and — for anything escalated or denied — a specific, honest sentence about what would change the outcome (a photo, a renewed policy, missing evidence), sourced from the same oracle logic that made the decision, not a canned FAQ.

08

Anticipated questions

Isn't this just a fairness linter with extra steps?

A linter tells you a rule was violated. This changes what the agent can see before it reasons, proves that change with a before/after context inspection, and then holds that fix in place with a regression suite that runs against every future version. The output is enforcement code, not a warning.

Could this generalize past insurance claims?

That's the actual design constraint, not an afterthought — FairClaim's agents never import from FailureFoundry's abi/ or enforcement/ modules; everything crosses through a trace/scenario layer. Swap the agents, keep the compiler.

What's simulated versus real, if I dig in?

The claims environment is synthetic by design (no real claimant data, per CLAUDE.md §7) and the oracle is a deterministic rule, not an LLM. Everything downstream of a claim entering the system — agent execution, traces, failure detection, ABI compilation, enforcement, metrics, regression, the release gate, and PRISM evidence — runs for real against a live account and a real SQLite system of record.

What would you build next with more time?

Neo4j as the causal-lineage projection layer is scoped but on standby in this environment; wiring it in would make the failure→ABI→mutation dependency tree queryable as a graph instead of joined tables. Multi-hop version comparison across more than two agent versions is the other natural next step.
